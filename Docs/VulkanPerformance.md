# PlagC Vulkan performance path

PlagC keeps the pinned Ogre-Next submodule immutable. Vulkan-specific fixes are generated by
`Build/Vulkan.lua` from exact, fail-closed patches in `Build/Patches`.

## Current presentation pipeline

The target Radeon/Windows run showed `vkQueuePresentKHR` spending roughly 3-4 ms of host time even
with `VK_PRESENT_MODE_IMMEDIATE_KHR`, while image acquisition was already about 0.06 ms. PlagC now
pipelines presentation as follows:

```text
Frame N render thread                 Presentation worker
--------------------                  -------------------
vkQueueSubmit
queue present request  -------------> vkQueuePresentKHR
return from renderOneFrame

Frame N+1
game / physics / animation           present host work continues
first swapchain use
wait only for residual present time
vkAcquireNextImageKHR
record / submit next frame
```

If graphics and presentation use the same `VkQueue`, submit and present take a shared mutex because
Vulkan requires host access to a queue to be externally synchronized. A dedicated present queue,
when one exists, does not use that serialization.

Presentation semaphore recycling remains image-lifetime based: a semaphore used by presentation is
returned to Ogre's available pool only after the corresponding swapchain image is acquired again.

## Runtime diagnostics

Release profiling prints these Vulkan-only lines every 240 samples:

```text
[PlagC Vulkan CPU] end-command-buffer avg=... max=...
[PlagC Vulkan CPU] submit-tail avg=... max=... queue-submit avg=... max=...
[PlagC Vulkan CPU] new-command-buffer tail-wait avg=... max=...
[PlagC Vulkan CPU] present-enqueue avg=... max=...
[PlagC Vulkan WSI] present avg=... max=... queue-delay avg=... main-wait avg=... max=...
[PlagC Vulkan WSI] acquire avg=... max=...
[PlagC Vulkan WSI] swapchain images=... requested=... frames-in-flight=... surface-min=... surface-max=...
```

`present avg` is the worker's host time inside the presentation path. `main-wait avg` is the part
that was not hidden by game work and therefore still contributes directly to the next render frame.
For CPU optimization decisions, `main-wait`, `queue-submit`, the two tail waits, and
`Ogre renderOneFrame` matter more than raw worker `present avg`.

## WSI tuning knobs

Defaults remain the measured stable settings. These environment variables are for controlled
benchmark matrices, not required launch settings:

```text
PC_VULKAN_FRAMES_IN_FLIGHT=2|3|4
PC_VULKAN_SWAPCHAIN_IMAGES=2..8
```

The swapchain request is clamped to the surface limits and never below the selected frame-in-flight
count. Leave `PC_VULKAN_SWAPCHAIN_IMAGES` unset to keep Ogre's default of frame slots plus one image.

Example Windows benchmark:

```bat
set PC_VULKAN_FRAMES_IN_FLIGHT=4
set PC_VULKAN_SWAPCHAIN_IMAGES=5
Sandbox.exe --renderer vulkan --performance-csv vulkan.csv --performance-warmup 240 --performance-seconds 30
```

Run the same scene without camera/input changes under OpenGL for comparison.

## Acceptance targets for the current scene

The Vulkan path is considered CPU-optimized for this workload when steady-state measurements show:

```text
Renderer submit / Ogre renderOneFrame   ~2-3 ms target
Renderer upload                         <= 0.5 ms
WSI acquire                             < 0.2 ms typical
WSI residual main wait                  as close to 0 ms as practical
Frame P99                               <= 9-10 ms
Hitches >16.7 ms                        0
Vulkan GPU total                        <= OpenGL GPU total
```

Raw `vkQueuePresentKHR` worker time does not need to be near zero if it is successfully overlapped;
the critical metric is how much of that time remains visible as `main-wait` on the render thread.

## Follow-up audit and update ownership

See [VulkanAudit20261029.md](VulkanAudit20261029.md) for current implementation status,
validation limits and remaining work. Dynamic vertex writes now coalesce per render
submission through a dirty-ID queue. Their map/copy time is included in renderer
submission; animation upload time alone must not be used to claim a speedup.
Vulkan timestamp readback batches a completed slot into one driver call and first
checks its owning frame so old query values cannot masquerade as a new sample.
